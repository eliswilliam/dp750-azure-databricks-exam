Quelle configuration adopter pour améliorer la disponibilité lors de la création répétée de calculs, éviter de dimensionner pour la demande maximale et réduire les frais ?
Propositions de réponse :
  • A. Utiliser des instances à la demande (on-demand), activer le dimensionnement automatique (autoscaling), et configurer l'arrêt automatique (auto-termination)

Vous avez une table Delta volumineuse qui subit fréquemment des requêtes filtrant sur une colonne de haute cardinalité (ex: `customer_id`). Le partitionnement traditionnel sur cette colonne a créé un problème grave de "petits fichiers". Quelle technique devez-vous utiliser ?
Propositions de réponse :
  • A. Repartitionner la table avec `df.repartition(100)` avant chaque écriture
  • B. Appliquer la commande `OPTIMIZE` avec l'indexation multidimensionnelle `ZORDER BY (customer_id)` ou activer le Liquid Clustering (Réponse correcte)

Pourquoi les autres options sont incorrectes :
  • Option A : `repartition()` réorganise le nombre de fichiers en mémoire lors de l'écriture mais ne réordonne pas logiquement les données par valeur de colonne.
  • Option C : Parquet standard ne gère ni le Z-Ordering ni les fonctionnalités d'optimisation avancées de Delta Lake.
  • Option D : Les tables Spark/Delta ne supportent pas les index secondaires SQL traditionnels des SGBD relationnels.

Un travail Spark volumineux échoue fréquemment en raison de problèmes de mémoire sur le Driver (Out Of Memory - OOM). Quelle est la meilleure action corrective concernant la configuration du cluster ?

  • A. Augmenter le nombre de nœuds Worker.
  • B. Activer uniquement l'auto-scaling.

  • Option B : L'auto-scaling ajuste le nombre de workers ; il n'accroît pas la RAM du nœud Driver.
  • Option C : Le mode Single-Node concentre driver et workers sur une seule machine et ne résout pas le manque de mémoire du Driver.

Dans Unity Catalog, quelle est la structure exacte du namespace à trois niveaux obligatoire pour référencer un objet de données (comme une table ou une vue) dans une requête SQL ?

Justification :
Unity Catalog utilise un espace de noms à trois niveaux strict : catalog.schema.table (ou vue, ou volume). Ce namespace est la clé de voûte de la gouvernance : les privilèges peuvent être accordés à chacun de ces niveaux.

  • Option B : Cette notation mélange un objet (table) et un attribut (colonne) : une colonne ne fait pas partie du namespace des objets.
  • Option D : Le metastore est un conteneur d'administration de niveau compte ; il n'apparaît pas dans le chemin à trois niveaux utilisé dans les requêtes.
